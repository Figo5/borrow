## Capture route and privacy

Use the native macOS recording interface through the approved computer-use controls. The Screenshot toolbar's selected-portion recording is a candidate route; first inspect the actual toolbar and available options on this Mac. Frame only the Borrow window and choose an explicit output location. Do not automate a separate capture route or enable a new permission without addressing the system prompt through the normal approval flow.

The current computer-use API exposes native app interaction and screenshots but no dedicated video-recording method. Availability of `ffmpeg` or `screencapture` on the machine does not itself establish screen-capture permission or authorization to record unrelated content. If native capture is unavailable, leave the video pending and retain this shot list.

Before recording, inspect the capture region for other windows, desktop contents, notifications, prompts, terminal output, journal filenames, paths, and unrelated recordings. Select only the intended sanitized run. No conversation content or code belongs in the public footage.

Save the user-facing video under the project output directory with a stable `Borrow-demo` filename. A release may link that artifact only after its playback and privacy review pass.

## Discover, rehearse, record

1. **Discover:** inspect the built native app, exact control labels, enabled modes, deadline display, actual assertion state, stop action, report, and native export flow. Do not script against guessed labels or old accessibility indices.
2. **Rehearse:** perform the same flow without recording. Confirm the mode and report agree, the hold is confirmed before it appears active, and stopping/finishing displays observed release rather than actual sleep.
3. **Record:** capture the genuine app behavior. Never inject demo-only successful states or replay a fixture as a physical test. Stop capture as soon as the intended flow is complete.
4. **Inspect:** play the entire video, verify readable text and timing, and inspect every scene for private content or unsupported claims. Correct capture or captions before release preparation uses it.

## Shot list

Target a concise 45–75-second edit. The actual physical interval remains 5–10 minutes and is represented as an explicitly labelled elapsed-time cut, not continuous screen evidence.

| Scene | What appears in Borrow | Narration/caption substance |
| --- | --- | --- |
| Start | Borrow's native window and mode selection | Temporary owned wake control plus evidence; no general closed-lid guarantee |
| Choose | Experimental AC hold and finite deadline, or supported idle mode if the experiment failed | Idle prevention does not prevent lid sleep; experimental mode requires AC and a real setup test |
| Attach | The deliberately selected session begins observation, with no picker path visible in the final footage | Borrow observes lifecycle events locally and discards conversation/tool content |
| Confirm | OS-confirmed owned hold and live recording | A helper launch alone is not protection; the shown state follows actual confirmation |
| Interval | Explicit elapsed-time cut to the real post-reopen recording | State the actual measured duration and whether ambient keep-awake software made attribution uncertain |
| Evidence | Relevant event counts, notifications/gaps, and logged outcome | Events/logged completion are evidence; they do not certify task correctness or continuous execution |
| Release | Borrow's own hold is confirmed released | Borrow stopped its own wake request; actual system sleep is a separate observation |
| Export | The sanitized report and limits | Share a reproducible report, with the exact setup and unresolved questions |

If the physical experiment is unsuccessful, the result scene should display that evidence and explain the limitation. A truthful failure demonstration is preferable to claiming charger-only operation from a successful open-lid test.
